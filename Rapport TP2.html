Résumé— Les étudiants consultent des annales avec une connexion souvent instable. Cette étude compare quatre réalisations de la même application, « Annales & Révisions ». Seule la version Node.js, écrite par Eliakim, est présente dans ce dépôt et a été mesurée. Le scénario commun a été exécuté une fois sur la machine de test : démarrage 46 ms, recherche « Maths L1 » 11 ms, dix téléchargements de 14 à 28 ms. Aucune conclusion comparative n’est possible tant que les trois autres versions n’ont pas produit leur propre mesures.csv.

Mots-clés— performance, Node.js, SQLite, annales, hors-ligne

I. Introduction

Le temps d’ouverture, de recherche et de téléchargement compte pour un étudiant qui paie ses données et dont le réseau coupe souvent. Une application lente ou impossible à relire hors-ligne rate son usage.

On entend souvent qu’une application de bureau ou mobile serait plus rapide qu’une application web, ou qu’un framework serait plus lent qu’un autre. Ces affirmations restent générales tant qu’elles ne portent pas sur les mêmes fonctions et les mêmes données [1].

Question de recherche : à fonctions et données égales, quelle technologie parmi Flutter, Java Swing, Node.js et Django traite le plus vite le scénario de consultation d’annales ?

Hypothèse de travail : la version dont le stockage et les fichiers restent sur la même machine devrait afficher des délais courts pour la recherche et le téléchargement local. Cette hypothèse n’est pas tranchée ici, faute des trois autres séries de mesures.

Ce document décrit l’application, le protocole, la version Node.js réalisée, et les mesures réellement produites par mesures.csv. Les sections suivantes suivent le modèle du TP.

II. Méthodologie

A. Application de référence

« Annales & Révisions » affiche 5 000 annales par pages de 20, filtre par faculté, année académique et matière, recherche un mot-clé dans le titre et la matière, télécharge un document seulement sur action de l’utilisateur, relit ce document depuis le stockage local, et ajoute ou retire un favori. Il n’y a pas de compte, de paiement, de notification, de commentaire ni de mode sombre.

Le fichier officiel commun des 5 000 annales n’a pas été déposé dans ce dossier. Le jeu utilisé est donc généré de façon déterministe, graine 20261116. Les quarante premières fiches sont Informatique, Maths, L1, afin que le scénario « Maths L1 » puis « Informatique » ait au moins dix documents. Les tailles vont de 50 000 octets à 500 000 octets. Ce jeu ne doit pas être présenté comme le fichier officiel s’il arrive plus tard.

Le cahier des charges proposait IndexedDB et la Cache API pour Node.js. La version remise utilise SQLite, sur demande explicite, pour le même rôle de stockage local que les versions Flutter et Java. Le module node:sqlite est encore marqué expérimental par Node.js [1].

C. Métriques

Le journal mesures.csv a l’en-tête evenement,timestamp_ms. Le temps est en millisecondes depuis l’époque Unix. Les durées ci-dessous sont des différences entre un événement de début et l’événement de fin correspondant. La lecture hors-ligne n’a, dans le cahier des charges, qu’un événement de fin : sa durée n’est donc pas calculée.

  • Démarrage : demarrage_fin moins demarrage_debut, en ms. Il couvre l’ouverture de SQLite et la mise en écoute du serveur.
  • Recherche : recherche_fin moins recherche_debut, en ms, pour la requête « Maths L1 ».
  • Téléchargement : telechargement_fin moins telechargement_debut, en ms, pour chaque fichier écrit sur le disque.

D. Outils et environnement de test

Aucun outil de charge externe n’a été utilisé. Le scénario est le script scripts/scenario.js, qui appelle le serveur déjà lancé. Machine : Windows 10.0.26200, Intel Core i7-13620H, 16 cœurs logiques, 16 045 Mo de mémoire. Serveur : http://127.0.0.1:3080. Journal activé par MESURES_ACTIVEES=true.

E. Déroulement des tests

  1. Démarrer node server.js avec MESURES_ACTIVEES=true.
  2. Lancer node scripts/scenario.js.
  3. Le script recherche « Maths L1 », filtre la faculté Informatique, télécharge les 10 premières annales du résultat, lit les 5 premières, ajoute 3 favoris.
  4. Lire mesures.csv. Ne pas y ajouter de chiffres à la main.

L’étape « couper le réseau » n’a pas été simulée par un outil. La lecture a utilisé le fichier déjà enregistré dans data/telecharges, le serveur local restant allumé. Un autre groupe peut refaire les étapes 1 à 4 telles quelles.

III. Développement

A. Réalisation des versions

Seule la version Node.js est dans ce dossier. Les classes sont Annale, GenerateurAnnales, BaseAnnales, JournalMesures, ServeurAnnales et, dans le navigateur, ApplicationAnnales. Il n’y a pas de dépendance npm : le serveur utilise les modules node:http et node:sqlite. Chaque téléchargement écrit un PDF dont la taille en octets est exactement taille_octets.

B. Équivalence fonctionnelle

Les versions Flutter, Java et Django ne sont pas dans ce dépôt. Leur équivalence n’a donc pas été vérifiée. Sur la version Node.js, le scénario a renvoyé 212 annales pour « Maths L1 » et 70 après le filtre Informatique, puis 10 téléchargements, 5 lectures et 3 favoris.

C. Difficultés rencontrées

Le fichier de données commun et le bloc de versions imposées manquaient. Le stockage demandé d’abord pour le web (IndexedDB) a été remplacé par SQLite. Un PDF de taille imposée a été construit en complétant le flux du document par des espaces, afin que la taille mesurée soit celle du cahier des charges.

B. Analyse

Sur cette machine et cette unique exécution, la version Node.js répond en moins de 50 ms au démarrage et en 11 ms à la recherche sur 5 000 lignes. Neuf téléchargements sur dix durent 14 à 17 ms ; un dure 28 ms. Ces chiffres décrivent un serveur local, pas un réseau mobile. Les figures du modèle, qui comparaient quatre technologies avec des valeurs fictives, ne sont pas reproduites : il n’y a pas quatre séries à tracer.

C. Interprétation et discussion

Les délais Node.js sont courts parce que la base, le script et les fichiers sont sur la même machine. Cela ne confirme pas que Node.js serait plus rapide que Flutter, Java ou Django. On ne peut pas conclure sur la question de recherche. Limites : une seule répétition, jeu de données de remplacement, quarante fiches forcées, module SQLite expérimental, réseau non coupé, pas de durée de lecture faute d’événement de début.

V. Conclusion

La question portait sur la technologie la plus rapide pour la même application d’annales. La version Node.js est terminée et son scénario a été mesuré. La réponse comparative n’est pas connue. La suite nécessaire est de déposer les mesures.csv de Princesses, Agostinho et Meshoullam, produits avec le même scénario, puis de remplir le tableau II sans réécrire les nombres.
